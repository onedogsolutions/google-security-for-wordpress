# State Tracker - Google Security for WordPress

## Current Phase: Phase 23 (MainWP child-side settings bridge)

### Phase 23 Modifications (v2.9.0)
- **MainWP child-side bridge.** New `includes/class-gswp-mainwp-child.php` (`GSWP_MainWP_Child`, constructed in `gswp_init()` right after `GSWP_Rest_Api`). Lets the already-shipped companion dashboard extension (`onedogsolutions/mainwp-for-google-security-for-wordpress` v1.0.0) read and write each child site's settings from a MainWP dashboard. The dashboard end already exists and currently resolves to its "bridge missing" state on every child because nothing hooked `mainwp_child_extra_execution` yet; this phase closes that gap. **PHP-only — nothing under `src/` or `assets/` changed, so no React/webpack rebuild.**
- **Transport.** MainWP Child's `extra_execution` callable runs `apply_filters( 'mainwp_child_extra_execution', $information, $post )` (with `$post = $_POST`) *after* its own RSA-signature verification, as the connected admin user, dispatched from `parse_init`/`init` priority 9999. Registering the bridge filter in `gswp_init()` on `plugins_loaded` priority 10 is safely earlier. Because the request is already authenticated and impersonating the admin, the bridge calls the REST **callbacks** directly and deliberately does **not** re-run `current_user_can()` — that is why the class does not touch the REST route or its `check_permissions()`.
- **Single-source validation.** `handle()` dispatches on `$post['mwpgswp_action']`: `get_settings` returns `(new GSWP_Rest_Api())->get_settings()->get_data()`; `update_settings` JSON-decodes `$post['settings']` (`wp_unslash`ed first — WordPress slashes superglobals), builds a `WP_REST_Request` for `POST /gswp/v1/settings`, copies each incoming key in with `set_param()`, and routes through `GSWP_Rest_Api::update_settings()`. So every rule stays in one place — threshold clamping, enum whitelists, alert-email validation, the alert-mode digest-cron reschedule, role validation against the child's real roles, and exempt-login resolution against the child's real users (which cannot be validated dashboard-side). Any future option wired into the REST route becomes MainWP-manageable automatically.
- **Wire-format contract (fixed — the extension is deployed).** Success (both actions) adds exactly one key: `$information['mwpgswp'] = array( 'success' => true, 'version' => GSWP_VERSION, 'woocommerce_active' => class_exists( 'WooCommerce' ), 'roles' => wp_roles()->get_names(), 'settings' => <full post-save settings map> )`. Failure (unknown action, undecodable payload) is `array( 'success' => false, 'error' => '…' )`. When `$_POST['mwpgswp_action']` is absent the filter returns `$information` **unchanged** — that absence of the `mwpgswp` key is how the dashboard tells "GSWP missing / older than 2.9.0" apart from an error, and it is what keeps the bridge invisible to every other extension that shares the `extra_execution` filter.
- **Inertness.** With MainWP Child absent, the class only registers a filter nobody fires: no output, no hooks on any core action, no front-end effect, and a normal MainWP sync passes through untouched (non-matching requests return `$information` as-is). Loaded unconditionally (required right after `class-gswp-rest-api.php`) because MainWP dispatches on the front end where `is_admin()` is false.
- **No changes** to `gswp_default_options()`, activation, migration, `GSWP_Rest_Api`, the REST route, options, or any existing class behaviour. Out of scope (mirrors the extension): no bulk/group apply, no 2FA user administration, no alert-log surfacing, no new REST routes — configuration transport only.
- Version bumped to 2.9.0 (main header, `GSWP_VERSION`, `readme.txt` stable tag + MainWP feature bullet + "Can I manage these settings from MainWP?" FAQ + changelog, `package.json`, `package-lock.json` root). `php -l` clean on both touched PHP files (`google-security-for-wordpress.php`, `includes/class-gswp-mainwp-child.php`). The new class file must ship in the distribution ZIP's explicit file list (the same list that excludes `tests/manual/` — see Phase 21); it is wired into the main file's `require_once` block so the plugin loads it.
- See `PLAN-gswp-2.9.0-mainwp-bridge.md` (companion repo) for the full spec, wire-format contract, reference implementation, and the staging round-trip verification checklist.

## Historical Phase: Phase 22 (Tabbed settings screen + 2FA button text-colour fix)

Replaced the `grid grid-cols-1 … md:grid-cols-2` panel stack in `src/components/App.jsx` with a new hand-rolled `src/components/SettingsTabs.jsx` implementing the WAI-ARIA tabs pattern (`role="tablist"`/`"tab"`/`"tabpanel"`, arrow-key + Home/End navigation, roving `tabindex`, focus moves to the newly active tab). This keeps the one Save button submitting the complete settings object regardless of which tab is showing, avoids re-triggering `animate-fadeIn` reveals on every switch, and needs no new CSS (Tailwind v4 preflight already ships `[hidden]{display:none!important}`).
- **Active tab persisted in the URL hash** (`#tab=<id>`), read on mount via `getTabFromHash()` (validated against the tab list, falling back to `credentials`) and written with `history.replaceState` on change — deep-linkable, no scroll jump, no history spam, no router dependency.
- **2FA button text-colour bug, root cause and fix.** The "Set up Two-Factor Authentication" button was rendering WP-admin link-blue text despite the Phase 8 white-text override (`.gswp-admin-isolated a.gswp-2fa-btn` + `:hover/:focus/:active`). That override lived inside `@layer base` in `src/styles/index.css`. Tailwind v4 emits genuine CSS cascade layers, but WordPress admin's own stylesheets (`a{color:#2271b1}`, `a:hover{color:#135e96}`, etc.) are unlayered — and per the CSS cascade spec, unlayered author styles always beat layered ones regardless of specificity. So WP's plain `a` rule won over both the `text-white` utility and the override, a regression from the Tailwind v4 migration (this worked when Phase 8 shipped, before the project was on layered Tailwind output). Fix: moved the four selectors out of `@layer base` to plain top-level CSS (after the `@theme` block gets built), added `:visited` for completeness, and documented why the rule must stay unlayered. Verified in the built `build/index.css` that the rule now sits after the closing of `@layer utilities{...}`, outside every layer.

Version bumped to 2.8.1 (main header, `GSWP_VERSION`, `readme.txt` stable tag + changelog, `package.json`, `package-lock.json` root) since no new options were added. React assets rebuilt (`npm run build`); `wp-scripts lint-js` and `lint-style` both clean.

## Historical Phase: Phase 21 (Application-password hardening for 2FA-enforced roles)

### Phase 21 Modifications (v2.8.0)
- Closed the last password-only authentication path for accounts our 2FA policy protects. Role-based enforcement only guaranteed a second factor on **interactive** logins; a REST API or XML-RPC login with an **application password** bypassed the challenge by design (`GSWP_Two_Factor::enforce_second_factor()` waves REST requests through, and application-password auth never reaches an interactive challenge). A new opt-in toggle disables application passwords for users in a 2FA-enforced role via the core `wp_is_application_passwords_available_for_user` filter, so a single credential can no longer authenticate an enforced `manage_options` account. Off by default (agency management tooling commonly connects via an admin application password, so on-by-default would sever those connections on a routine update).
- **Bug fixed in the same phase:** `GSWP_Two_Factor::block_non_interactive()` — the XML-RPC block for enrolled users the readme/STATE.md have advertised since v2.0.0 — **had never been hooked** (added in the rebrand commit, no `add_filter` anywhere in history). An enrolled user's real password worked over XML-RPC with no second factor. It is now wired to `authenticate` at priority 99 (after the password/reCAPTCHA/Account Defender checks at 20/30/40, just before the interactive challenge at 100), restoring the documented behaviour. It stays scoped to **enrolled** users (enforcement locks the dashboard, not authentication, so an enforced-but-unenrolled user's XML-RPC password login is no stricter than their interactive one).
- **Mechanism.** New `restrict_app_passwords( $available, $user )` on `wp_is_application_passwords_available_for_user` (priority 10) returns `! role_is_enforced( $user->ID )` when the block is on — but only ever **narrows** an already-true `$available` (returns the incoming value, never a hard `true`), so it composes with other plugins that disable application passwords. Returning `false` closes every application-password surface at once: authentication with already-issued passwords (REST **and** XML-RPC, since core's `wp_authenticate_application_password()` handles both), the profile "Application Passwords" section, the REST management endpoints, and `authorize_application.php`. Existing passwords are **rejected, not revoked** (stored meta untouched), so turning the toggle off restores them instantly with no re-issuing. Two new static predicates mirror `remember_enabled()`: `app_password_block_enabled()` (master switch + `gswp_2fa_block_app_passwords`) and `is_app_password_exempt( $user )`.
- **Scope = enforced roles, not enrolled users** (an app password minted before enrolment would otherwise be a permanent bypass; and a user who *voluntarily* enrolled in an un-enforced role never has an integration break). **No grace-period interaction** — the block applies the moment the toggle is on (grace is a dashboard-UX affordance; app passwords aren't part of 2FA setup). The 2FA master switch off unregisters both new hooks, so it doubles as a kill switch.
- **Per-account exemption list** (`gswp_2fa_app_password_exempt_users`, default `''`), added for the agency's real tooling: **MCP-server connections authenticate with application passwords on admin accounts**. The exemption is surgical — it re-allows application passwords only; the account still gets the interactive 2FA challenge and every other control. Comma-separated logins, validated at save time in the REST route (`sanitize_user()` each, kept only when `get_user_by( 'login', … )` resolves, de-duplicated, re-joined) so typos are dropped rather than silently never matching; matched case-insensitively against `$user->user_login`. Standard MainWP Child connections use their own RSA-key handshake (not application passwords) and are unaffected — verified as part of rollout.
- Settings: new options `gswp_2fa_block_app_passwords` (`'0'`) and `gswp_2fa_app_password_exempt_users` (`''`), wired through `gswp_default_options()`, REST `get_settings`/`update_settings` (boolean toggle + the validate-and-rejoin exempt list), the admin localizer, `App.jsx` defaults, and a new toggle row + reveal-on-enable "Exempt accounts" text input inside the existing "Require for roles" section of `src/components/TwoFactorNotice.jsx` (with warning copy about the immediate effect on existing application passwords and the recommendation to use a dedicated service account). Updated the now-accurate comment in `enforce_second_factor()`.
- Version bumped to 2.8.0 (main header, `GSWP_VERSION`, `readme.txt` stable tag + feature bullet + FAQ + changelog including the XML-RPC fix, `package.json`, `package-lock.json` root). React assets rebuilt (`npm run build`); `php -l` clean on all touched PHP, `wp-scripts lint-js` clean on the JSX.
- **Verified on staging** (WordPress 6.4.3, via Novamira MCP PHP execution driven by a local LLM): all 13 checks passed — baseline auth, block-on refusal (`application_passwords_disabled_for_user`), exemption re-allow with non-exempt still refused, rejected-not-revoked reversibility, connecting MCP account unaffected, and the XML-RPC block (`gswp_2fa_required` for an enrolled user, non-enrolled untouched). The chunked test scripts are committed under `tests/manual/` (excluded from the distribution ZIP, which copies an explicit file list). Verification also surfaced a live site where the exemption option held an *array* (external tooling); `is_app_password_exempt()` now normalizes an array value by imploding it instead of the `(string)` cast that would warn and match nobody.
- Docs: corrected the stale checkout-block FAQ (block checkout protected since 2.5.0) and added a service-account setup FAQ (create → optionally enrol → **exempt before minting**, since the block hides the Application Passwords UI for non-exempt enforced accounts → mint named app password → enable policy with only service accounts exempt → cut over and revoke human app passwords → rotate/monitor). The FAQ is the seed for expanded standalone docs (planned follow-up).
- Out of scope (roadmap): per-user exemptions as scattered profile checkboxes (kept central in one settings screen instead); revoking/auditing existing application passwords (core's profile screen already lists per-user passwords); blocking XML-RPC entirely for enforced-but-unenrolled users (stricter than the interactive baseline); an email alert on a blocked application-password attempt (would ride the Phase 20 action-hook seam).

## Historical Phase: Phase 20 (Admin email alerts on flagged events)

### Phase 20 Modifications (v2.7.0)
- Turned the two highest-value security signals the plugin already detects into an email to the operator, instead of a log line nobody watches: **Account Defender flagging `SUSPICIOUS_LOGIN_ACTIVITY` on an administrator-capable account**, and **Transaction Defense blocking a high-risk checkout** (both the classic checkout and the WooCommerce Checkout block). Big operational win for an agency running many sites; the hard requirement was throttling so it never becomes spam.
- **Decoupled detection from delivery via internal action hooks.** The detection sites fire plain actions — `do_action( 'gswp_suspicious_admin_login', $user, $labels, $context )` and `do_action( 'gswp_checkout_blocked', $risk, $threshold, $context )` — and the new `GSWP_Alerts` is the only shipped subscriber, keeping mail logic out of the verifier/defender classes and leaving the actions as a seam for future Slack/webhook forwarding. The actions fire whenever the source feature detects the event (independent of whether alerts are enabled); `GSWP_Alerts` only hooks them when `gswp_alerts` is on.
- New `includes/class-gswp-alerts.php` (`GSWP_Alerts`, constructed in `gswp_init()`). Two-layer **throttle pipeline** (the core of the feature): (1) per-event dedupe — a transient `gswp_alert_dedupe_{md5(key)}` keyed `login_{user_id}` (6 h window) or `checkout_{md5(billing_email ?: ip)}` (1 h window) suppresses repeats of the same event; (2) a global circuit breaker — a rolling hourly counter transient caps immediate sends at 5 (filter `gswp_alert_hourly_cap`), and anything past the cap (or anything at all in a digest mode) is appended to a queue (`gswp_alert_queue`, autoload-off, capped at 100 with a dropped-count) that the digest cron flushes as **one** summary email. Delivery mode `gswp_alert_mode` ∈ `immediate` | `hourly` | `daily`; digest modes never mail immediately and an empty period sends nothing. Emails are **sent on `shutdown`** so a slow mailer never delays the login/checkout response; `wp_mail` failures are logged under verbose logging and otherwise ignored (fail-open). Recipients come from `gswp_alert_email` (comma-separated, each `sanitize_email`/`is_email`-validated) and fall back to `admin_email`. Plain-text emails; subject/body lead with the site name since an agency watches many sites.
- **Detection wiring.** `GSWP_Account_Defender::capture_login_assessment()` now, on any `SUSPICIOUS_LOGIN_ACTIVITY` label (independent of the `gswp_ad_step_up` branch), resolves the flagged account — `$user` when the password was correct, else `get_user_by( 'login'|'email', $username )` so a wrong-password credential-stuffing attempt still resolves — and fires `gswp_suspicious_admin_login` when it passes `user_can( $target, apply_filters( 'gswp_alert_login_capability', 'manage_options' ) )`. `GSWP_Verifier::process_fraud_prevention()` (classic) and `GSWP_Blocks::validate_store_checkout()` (Store API) fire `gswp_checkout_blocked` inside their existing `risk >= threshold` block branches, alongside the existing log line, passing billing/total context (from `$_POST`+cart classically, from the `$order` in the block path). No behaviour change to either block.
- **Cron lifecycle.** `GSWP_Alerts::maybe_schedule_digest()` (on `init`, always registered) reconciles the `gswp_alerts_digest_event` schedule to the mode: scheduled at the mode's recurrence for digest modes, scheduled hourly only while an overflow queue exists in immediate mode, and cleared when the feature is off or the mode's recurrence changes. The REST route clears the event on a mode change so the next load reschedules it; a new `gswp_deactivate()` (`register_deactivation_hook`, the plugin's first) clears it on deactivation.
- Settings: new options `gswp_alerts` (default `0`), `gswp_alert_email` (`''`), `gswp_alert_mode` (`immediate`), `gswp_alert_login`/`gswp_alert_checkout` (per-event sub-toggles, default `1`), wired through `gswp_default_options()`, REST `get_settings`/`update_settings` (toggles in the `$toggles` array; `alert_email` validated+re-joined; `alert_mode` whitelisted with cron-clear on change), and the admin localizer. New React panel `src/components/AlertSettings.jsx` (master toggle, recipients input, delivery select, two event sub-toggles with the checkout one gated on `woocommerceActive`, and the standard classic-key Enterprise notice) rendered in `App.jsx` with the five defaults added.
- Version bumped to 2.7.0 (main header, `GSWP_VERSION`, `readme.txt` stable tag + feature bullet + changelog, `package.json`, `package-lock.json` root). React assets rebuilt (`npm run build`); `php -l` clean on all touched PHP, `wp-scripts lint-js` clean on the JSX.
- Out of scope (roadmap): Slack/webhook delivery (the two actions are the seam); alerts for non-admin suspicious logins, `SUSPICIOUS_ACCOUNT_CREATION`, or account-modification events; a cross-site agency dashboard; HTML email templates.

## Historical Phase: Phase 19 (Account Defender step 3 — account-modification events)

### Phase 19 Modifications (v2.6.0)
- Completed the reCAPTCHA Enterprise **Account Defender** console checklist by extending it from the front door (login/registration) to **account-modification events**: password resets, email-address changes, and two-factor enable/disable now carry the same anonymous, salted `accountId` and are annotated `LEGITIMATE` when they complete, so Google's site-specific model learns what a real owner's in-account activity looks like — the takeover signal that was missing. **Account changes are only assessed and annotated, never blocked** (these are authenticated users; a low score must not lock someone out of their own profile).
- New sub-toggle `gswp_ad_events` (default `1`) under the Account Defender panel, gating a new `GSWP_Account_Defender::events_active()` (Enterprise + `gswp_account_defender` + `gswp_ad_events`). Enabling Account Defender therefore completes the checklist out of the box, but a site that objects to Google JS on `profile.php`/account pages can switch just the modification events off without losing login coverage. Wired through `gswp_default_options()`, REST `get_settings`/`update_settings`, the admin localizer, `App.jsx` default, and a third toggle row in `src/components/AccountDefender.jsx` ("Assess account changes").
- `GSWP_Verifier`: extended the `build_account_user_info()` context whitelist with `wp_lostpassword`, `password_reset`, and `account_update` so `event.userInfo.accountId` is attached on those assessments too (login/registration unchanged). No other verifier change — `verify_token()` already accepts the identifier and captures the assessment name/labels.
- `GSWP_Account_Defender` (new "account-modification events" section, registered only when `events_active()`): injects the token field into the **own-profile** form (`show_user_profile`, priority 1) and loads the reCAPTCHA script on `profile.php` **only** (`admin_enqueue_scripts` — never `user-edit.php`, so an admin editing another user is never attributed to that account); assesses a sensitive self-profile save on `user_profile_update_errors` (email/password/2FA change detected) and annotates the committed outcome on `profile_update`; injects + assesses + annotates the **WooCommerce "Account details"** form (`woocommerce_edit_account_form` / `woocommerce_save_account_details_errors` / `woocommerce_save_account_details`). A single reCAPTCHA action (`account_update`) per form (tokens are single-use), with the terminal hooks deciding the annotation; a shared request-scoped guard (`$modification_annotated`) makes the profile_update annotation (fired inside `wp_update_user`) and the WooCommerce annotation idempotent. Added a small self-expiring **pending-assessment store** (`store_pending()`/`take_pending()`, transients) for the two deferred flows — the profile email-change confirmation link and the password-reset email link — which complete in a later request with no token; they're annotated once email control is proven.
- `GSWP_Login` owns the **password-reset lifecycle** (it already owns the wp-login.php forms): `validate_lostpassword()` now takes the requested `WP_User` (2nd arg of `lostpassword_post`), attaches the accountId, and stashes the assessment as pending `lostpw_{ID}`; new `resetpass_form` field injection (action `password_reset`, added to the `#resetpassform` selector in the login bootstrap JS), `validate_password_reset` assessment (guarded to the actual submission, not the GET render, and never blocking), and `after_password_reset` annotation of both the reset-form assessment and the stashed lost-password assessment. Script printing now also fires when only the reset path is active. WooCommerce resets that bypass `validate_password_reset` still get the lost-password pending annotated via core `after_password_reset`.
- `GSWP_Two_Factor::save_profile()`: on a successful self-service enable/disable it calls `GSWP_Account_Defender::note_2fa_change('enabled'|'disabled')` instead of annotating inline. **Implementation note / deviation from the plan:** `personal_options_update` (where `save_profile` runs) fires *before* `edit_user()` creates the `account_update` assessment (`user_profile_update_errors`), so inline annotation there would have no assessment yet; the flag is read at `profile_update` and enrolment adds the `PASSED_TWO_FACTOR` reason. Admin-initiated 2FA resets for another user are never annotated (not self-service).
- Version bumped to 2.6.0 (main header, `GSWP_VERSION`, `readme.txt` stable tag + feature bullet + changelog, `package.json`, `package-lock.json` root). React assets rebuilt (`npm run build`); `php -l` and `wp-scripts lint-js` clean.
- Out of scope (roadmap): **step 4 — site-wide passive telemetry script** (loading reCAPTCHA on every front-end page for continuous behavioural signal), to ship as its own opt-in, default-off, per-client toggle since it trades page weight for signal.

## Historical Phase: Phase 18 (WooCommerce Blocks / Store API checkout support)

### Phase 18 Modifications (v2.5.0)
- Closed the biggest coverage gap: the modern **WooCommerce Checkout block** submits over the **Store API**, so none of the classic-checkout hooks fired — a store using the block silently got **zero reCAPTCHA scoring and zero Transaction Defense** (the Mad Dog near-miss). The block is now protected by the same scoring, thresholds, and Enterprise Transaction Defense as the classic shortcode checkout, with no new settings (`gswp_enable_checkout` and the existing thresholds apply to both).
- New `includes/class-gswp-blocks.php` (`GSWP_Blocks`, constructed in `gswp_init()` with the shared verifier). Registers the JS integration on `woocommerce_blocks_checkout_block_registration`, declares the `gswp` checkout extension schema via `woocommerce_store_api_register_endpoint_data()` (`CheckoutSchema::IDENTIFIER`, falling back to the literal `'checkout'`) on `woocommerce_blocks_loaded`, and scores the token on `woocommerce_store_api_checkout_update_order_from_request`. It reads the token from `$request['extensions']['gswp']['token']`, calls `GSWP_Verifier::assess_checkout_token()`, and on failure throws a `RouteException` (HTTP 400) so the block surfaces the message — the Store API equivalent of a checkout validation error. On success it writes `_gswp_assessment_name` (the `GSWP_Transaction_Defense::META_ASSESSMENT` constant) and a risk order note directly on the order (no WC-session bounce needed), and enforces the opt-in high-risk block (`gswp_txn_block` / `gswp_threshold_txn`). Inert unless WooCommerce Blocks is present.
- New `includes/class-gswp-blocks-integration.php` (`GSWP_Blocks_Integration implements Automattic\WooCommerce\Blocks\Integrations\IntegrationInterface`), required lazily from the registration hook so the plugin stays parseable without Blocks. `initialize()` registers the Google reCAPTCHA loader (`enterprise.js`/`api.js`) and the block script with dependency handles `wp-element`, `wp-plugins`, `wp-data`, `wp-i18n`, `wc-blocks-checkout`, `google-recaptcha-v3`, and localizes `gswpBlocksData` (siteKey, isEnterprise, enabled).
- New hand-written asset `assets/js/gswp-blocks-checkout.js` (no build step, mirroring `gswp-2fa-modal.js`; reads runtime globals). Registers an invisible `ExperimentalOrderMeta` fill via `registerPlugin` (scope `woocommerce-checkout`); inside the fill it keeps a fresh reCAPTCHA token in the checkout extension data (`setExtensionData('gswp','token',…)`), priming on mount, refreshing on a 90s interval, and refreshing on the rising/falling edges of the checkout store's processing state (single-use tokens need a fresh one for retries). The **server enforces the policy** — a missing/low token blocks the checkout — so if reCAPTCHA fails to load the classic-parity missing-token block still applies.
- `GSWP_Verifier` refactor (additive, backward-compatible): `verify_token()` gained an optional 5th `$token` param (defaults to reading the posted `g-recaptcha-response` field, so every existing caller is unchanged); extracted a shared `format_address()` used by both the posted-field and order-based builders; added `build_checkout_event_extra_from_order()`, `build_transaction_user_from_order()`, `build_transaction_items_from_order()` (build Enterprise `transactionData` from a `WC_Order` since the Store API carries no `$_POST`); added the public `assess_checkout_token( $token, $order )` and a `get_last_fraud_risk()` getter. `GSWP_Transaction_Defense` is unchanged — its `woocommerce_order_status_changed` annotation already fires for block orders once the assessment meta is present.
- Bumped version to 2.5.0 (main header, `GSWP_VERSION`, `readme.txt` stable tag + features + changelog, `package.json`, `package-lock.json` root). The block script ships as a plain committed asset, so no webpack rebuild is required for this feature.

## Historical Phase: Phase 17 (2FA enforcement grace period + settings background fix)

### Phase 17 Modifications (v2.4.0)
- Added a configurable **grace period** to role-based 2FA enforcement so client rollouts can enable enforcement without instantly locking users out. New option `gswp_2fa_grace_days` (default `14`, clamped 0–30 by REST; `0` = the old immediate behaviour).
- `GSWP_Two_Factor::maybe_enforce_setup()` now consults `grace_deadline( $user_id )` before redirecting: within the window it registers an `admin_notices` countdown (`render_grace_notice()` — days remaining, localized deadline date via `date_i18n`, and a "Set up now" button to `profile.php#gswp-2fa`) and lets the dashboard work normally; past the deadline the existing profile lock/redirect applies.
- The per-user clock starts on the user's **first admin visit while enforcement applies** (`gswp_2fa_grace_start` user meta, set lazily in `grace_deadline()`), so users hired or role-enforced later get the same full window. The meta is cleared on successful enrolment (`save_profile`) and by `disable_for_user()` so an admin 2FA reset (lost device) grants a fresh window instead of an instant lockout.

When login protection is enabled, `replace_module_recaptcha()` (hooked to `fl_builder_render_module_content`) strips the module's own reCAPTCHA/hCaptcha field and dequeues its `g-recaptcha`/`h-captcha` loaders so this plugin's site-wide reCAPTCHA is the only one on the form. Inert unless `BB_PowerPack` is active.
